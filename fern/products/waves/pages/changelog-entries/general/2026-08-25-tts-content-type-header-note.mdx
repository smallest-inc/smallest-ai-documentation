---
title: "TTS API-ref: response `Content-Type` is `audio/wav` regardless of `output_format`"
---

The Lightning v3.1 / v3.1 Pro synchronous TTS endpoint always sets the response `Content-Type` header to `audio/wav`, even when `output_format` is `mp3`, `pcm`, `ulaw`, or `alaw`. The bytes in the body still match the requested format (a `mp3` request returns MPEG-1 Layer III; `file(1)` and the `ID3` / `0xFF Fx` frame-sync bytes confirm), but downstream consumers that MIME-sniff the `Content-Type` header (WhatsApp Cloud API media upload, some browsers, some S3 uploaders) will treat the payload as WAV unless the MIME is overridden client-side.

The API reference now documents this on the `output_format` field and on the `200` response block. Recommended overrides:

- `mp3` → `audio/mpeg`
- `wav` → `audio/wav`
- `ulaw` / `alaw` → `audio/basic`
- `pcm` → no registered MIME (treat as raw signed 16-bit LE at the requested `sample_rate`)

The request `Accept` header is not honored either. Only `output_format` in the body controls what is returned.

Verified against the platform source: `res.setHeader("Content-Type", "audio/wav")` is hardcoded across all TTS controllers and the Zod validator's `output_format` enum is `["wav", "ulaw", "alaw", "pcm", "mp3"]`. Other formats (`ogg`, `opus`, `aac`) return HTTP 400 `invalid_enum_value`.
